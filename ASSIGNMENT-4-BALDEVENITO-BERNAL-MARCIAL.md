# Assignment 4: Oracle Generation with Daikon

## Phase 1: Instrumentation and Trace Collection

### 1.2 Executed Commands

We collected traces from five execution sources: the manual unit test suite, the tests generated by **Randoop**, the games played by the **CLI Fuzzer**, the tests generated by **EvoSuite**, and the combination of **EvoSuite + Fuzzer**. All commands are run from the repository root, with Java 11. Traces are stored in `daikon-traces/` and invariants in `daikon-invariants/`.

#### 1. Manual Unit Test Trace

```bash
mvn clean test-compile

CP="lib/daikon.jar:target/classes:target/test-classes:$(mvn -q dependency:build-classpath -Dmdep.includeScope=test -DforceStdout)"

java -cp "$CP" daikon.Chicory \
    --ppt-select-pattern='^ar\.edu\.unrc\.game2048\.(Board|Cell)(\.|:::)' \
    --dtrace-file=ConsoleLauncherManual.dtrace.gz \
    --output-dir=daikon-traces \
    org.junit.platform.console.ConsoleLauncher \
    --select-class=ar.edu.unrc.game2048.CellTest \
    --select-class=ar.edu.unrc.game2048.BoardTest

java -cp lib/daikon.jar daikon.Daikon \
    -o daikon-invariants/ConsoleLauncherManual.inv.gz \
    daikon-traces/ConsoleLauncherManual.dtrace.gz \
    > daikon-invariants/daikon-output-manual.txt
```

#### 2. Randoop Automated Test Trace

```bash
mvn clean test-compile

CP="lib/daikon.jar:target/classes:target/test-classes:$(mvn -q dependency:build-classpath -Dmdep.includeScope=test -DforceStdout)"
```

### 1.3 Generated Files

The executions produced the following files:

**Traces (`daikon-traces/`):**

* `ConsoleLauncherManual.dtrace.gz`: Trace of the manual test executions.
* `ConsoleLauncherRandoop.dtrace.gz`: Trace of Randoop's exploratory executions.
* `FuzzerCLI.dtrace.gz`: Trace of a massive game generated by the Fuzzer.
* `evosuite.dtrace.gz`: Trace of the tests generated by EvoSuite.
* `fuzzer1.dtrace.gz` … `fuzzer5.dtrace.gz`: Traces of the 5 fuzzer games used together with EvoSuite.

**Invariants (`daikon-invariants/`):**

* `daikon-output-manual.txt` and `ConsoleLauncherManual.inv.gz`: Invariants of the manual suite.
* `daikon-output-randoop-fuzzer.txt` and `ConsoleLauncherRandoop.inv.gz`: Invariants of the extended Randoop + Fuzzer trace.
* `daikon-output-evosuite.txt` and `ConsoleLauncherEvosuite.inv.gz`: Invariants of the EvoSuite tests.
* `daikon-output-evosuite-fuzzer.txt` and `ConsoleLauncherEvosuiteFuzzer.inv.gz`: Invariants of the extended EvoSuite + Fuzzer trace.

The `.txt` files are Daikon's plain-text output; the `.inv.gz` files contain the same invariants serialized in binary format, which can be reprinted with `daikon.PrintInvariants`.

By using the `--ppt-select-pattern` selection patterns, we restricted monitoring exclusively to the methods and state of the domain classes `Board` and `Cell` (plus `MainCLI` for the CLI fuzzer), avoiding the noise and overhead of Java libraries and JUnit internals. Traces combined in the same inference must use the same pattern; otherwise, Daikon fails with *"Duplicate declaration of program point"*.

### 1.4 Adaptations for the EvoSuite Tests

The Chicory command from steps 1 and 2 did not work with the EvoSuite tests (`Cell_ESTest` and `Board_ESTest`):

1. **Empty classpath:** with `-DforceStdout`, Maven does not print the dependencies. This goes unnoticed in steps 1 and 2 because `daikon.jar` already includes JUnit, but the EvoSuite tests also need its runtime. We saved the classpath to a file with `-Dmdep.outputFile`.
2. **Chicory broke EvoSuite:** it instrumented every class. We restricted it to `Board` and `Cell` with the same `--ppt-select-pattern` used in steps 1 and 2.
3. **Incompatible Java versions:** `EvoRunner` needs Java 8 and Daikon needs Java 11. We converted the tests into plain JUnit 4 tests, without `EvoRunner` or scaffolding.
4. **Giant boards:** two tests create boards larger than 1000×1000 that corrupt or inflate the trace. We excluded them (79 of 81 tests run).

Everything was automated in `scripts/daikon-evosuite.sh`:

| Step | What the script does |
| :--- | :--- |
| **1** | Compiles and saves the classpath to `target/cp.txt`. |
| **2** | Copies the EvoSuite tests to `target/daikon-es-src/` with the adaptations above and compiles them. The original tests are not modified. |
| **3** | Runs Chicory with `org.junit.runner.JUnitCore` and generates `daikon-traces/evosuite.dtrace.gz`. |
| **4** | Runs Daikon and generates `daikon-invariants/ConsoleLauncherEvosuite.inv.gz` and `daikon-invariants/daikon-output-evosuite.txt`. |

> The unadapted EvoSuite tests (with `EvoRunner`) still need Java 8. To run them with Maven: `mise exec java@temurin-8 -- mvn test -Pevosuite`.

### 1.5 Adaptations for Combining EvoSuite with the Fuzzer

EvoSuite provides variety of **objects** (boards of many sizes, `AddRandomTile`, exceptions), but not of **values**: it searches for code coverage rather than playing games, and the maximum score in its trace was 16. To cover that gap, we combined its trace with random games from the Assignment 3 fuzzer. Everything is in `scripts/daikon-evosuite-fuzzer.sh`:

| Step | What the script does |
| :--- | :--- |
| **1** | Runs `scripts/daikon-evosuite.sh` and obtains `daikon-traces/evosuite.dtrace.gz` (section 1.4). |
| **2** | Plays 5 games in the CLI under Chicory, with the same `--ppt-select-pattern` as the EvoSuite trace. The moves are generated by `RandomFuzzer` from `fuzzer.py` (between 1000 and 3000 per game) with fixed seeds, so the result is reproducible. Generates `daikon-traces/fuzzer1.dtrace.gz` … `fuzzer5.dtrace.gz`. |
| **3** | Runs Daikon on the 6 traces together and generates `daikon-invariants/ConsoleLauncherEvosuiteFuzzer.inv.gz` and `daikon-invariants/daikon-output-evosuite-fuzzer.txt`. |

> The command from the assignment, `python3 fuzzer.py | java ... MainCLI`, does not work with our `fuzzer.py`: its `main()` runs the game on its own and only prints a summary. That is why the `RandomFuzzer` class is used directly.

The 5 games ended with scores of 568, 676, 944, 1356, and 2268. The results are analyzed in section 3.4.2.

## Phase 2: Invariant Inference

### 2.1 Program Points and Reported Invariants (Manual Trace)

In the first run over the manual suite, Daikon grouped its findings into the following program points:

| Class | Observed moment | Observed points | Reported invariants | Representative example |
| :--- | :--- | :---: | :---: | :--- |
| `Cell` | `CLASS` | 1 | 3 | `Cell.EMPTY.value == 0` |
| `Cell` | `OBJECT` | 1 | 2 | `this.value >= 0` |
| `Cell` | `ENTER` | 8 | 8 | `Cell.Cell(int):::ENTER`: `value >= 0` |
| `Cell` | `EXIT` | 29 | 104 | `Cell.getValue():::EXIT`: `this.value == return` |
| `Board` | `CLASS` | 1 | 0 | No invariants reported. |
| `Board` | `OBJECT` | 1 | 12 | `this.score >= 0`, `this.grid != null` |
| `Board` | `ENTER` | 23 | 106 | Entry points of constructors and methods. |
| `Board` | `EXIT` | 65 | 499 | `Board.Board():::EXIT`: default size and zero score. |

* **Total Program Points (PPTs):** 129
* **Total Reported Invariants:** 734

### 2.2 Representative Examples

We selected invariants that faithfully reflect the expected behavior and the rules of the game:

* `Cell:::OBJECT` $\rightarrow$ `this.value >= 0`: Guarantees the lower bound of a cell's value.
* `Cell.getValue():::EXIT` $\rightarrow$ `this.value == return`: Confirms the consistency of the getter.
* `Cell.isEmpty():::EXIT` $\rightarrow$ `(this.value == 0) <==> (return == true)`: Bidirectional relation between emptiness and the value $0$.
* `Cell.canMergeWith(...):::EXIT;condition="return == true"` $\rightarrow$ `this.value == other.value`: Confirms that cells must have equal values to merge.
* `Board:::OBJECT` $\rightarrow$ `this.score >= 0`: The game score can never be negative.
* `Board:::OBJECT` $\rightarrow$ `this.size == size(this.grid[])`: Consistency between the `size` attribute and the rows of the matrix.
* `Board.Board():::EXIT` $\rightarrow$ `this.score == 0`: The initial board state always starts with a score of zero.
* `Board.applyMove(...):::EXIT` $\rightarrow$ `this.score >= orig(this.score)`: Guarantees that the score is monotonically non-decreasing after a move.

### 2.3 Non-Representative Examples (Manual Trace)

We identified invariants inferred due to the lack of variability in the executed manual tests:

* `Cell.canMergeWith(...):::EXIT;condition="return == true"` $\rightarrow$ `this.value one of {2, 4}`: Assumes that only values 2 and 4 can merge, ignoring higher values such as 8 or 16.
* `Cell.mergeWith(...):::EXIT` $\rightarrow$ `return.value one of {4, 8}`: Restricts the merge result to only 4 or 8.
* `Board:::OBJECT` $\rightarrow$ `this.score % this.size == 0`: Arithmetic coincidence with no basis in the domain rules.

### 2.4 Observations on the Inference

1. **Calls without a return:** 26 executions threw exceptions expected by the unit tests. Daikon discarded their `EXIT` points, so the invariants only reflect calls that returned normally.
2. **Small-input bias:** Most of the extreme generalizations in the manual suite come from the use of small, initial values in the tests.

## Phase 3: Inspection and Evaluation of the Invariants

### 3.0 Classification Used

* **Correct and useful:** A genuine property of the program with real ability to detect failures.
* **Correct but trivial:** True by definition, but with low detection value.
* **Too strong:** The product of an insufficient set of traces (*overfitting*).
* **Incorrect:** False with respect to the actual specification.

### 3.1 Evaluation of `Cell` (Initial Trace)

| # | Invariant | Program point | Correct? | Useful? | In `repOK()` | Classification |
| :-: | :--- | :--- | :-: | :-: | :-: | :--- |
| 1 | `this.value >= 0` | `Cell:::OBJECT` | Yes | Yes | Yes | **Correct and useful** |
| 2 | `this.value >= Cell.EMPTY.value` | `Cell:::OBJECT` | Yes | No | Yes | **Correct but trivial** |
| 3 | `this.value == orig(value)` | `Cell.Cell(int):::EXIT` | Yes | Yes | No | **Correct and useful** |

### 3.3 Counterexamples for Too-Strong Invariants

* **`this.value one of {2, 4}` in `canMergeWith`:** Creating `new Cell(8)` and calling `canMergeWith(new Cell(8))` returns `true`, violating the restricted set `{2, 4}`.
* **`this.spawner` always of type `AddTileDeterministic`:** The real game uses `AddRandomTile`. Creating the class through the production constructor violates this rule.
* **`this.score % this.size == 0`:** On a board of size $3$, a move that merges two cells of value $2$ adds $4$ points to the score. Note that $4 \bmod 3 = 1 \neq 0$.
* **`Board.WINNING_VALUE > this.score`:** In a long game the score can exceed 2048 points. Neither the manual tests nor the EvoSuite tests play long games (with EvoSuite the maximum score was 16); the fuzzer games do refute it, with a score of 2268 (see 3.4.2).
* **`Board.DEFAULT_SIZE != size(this.grid[])-1`:** Equivalent to "the size is never 5". Creating `new Board(5)` violates it; no suite created a 5x5 board.

### 3.4 Improving Trace Coverage

To evaluate the impact of execution diversity on oracle quality, we extended the manual trace in two ways: combining **Randoop + Fuzzer** (3.4.1) and combining **EvoSuite + Fuzzer** (3.4.2).

#### 3.4.1 Extended Trace with Randoop + Fuzzer

We collected an extended trace combining **Randoop**'s automatic exploration and the massive games of the **CLI Fuzzer** (`ConsoleLauncherRandoop.dtrace.gz` and `FuzzerCLI.dtrace.gz`).

| Metric | Original Trace (Manual Tests) | Extended Trace (Randoop + Fuzzer) |
| --- | --- | --- |

| **New genuine invariants** | Direct assignment coincidences. | **Discovered:** $2 \times \text{this.value} = \text{return.value}$ in `mergeWith()`, score preservation in `applyMove()`, and range preconditions. |

| **Exceptions / Error paths (no return)** | 26 | 348 |

**Did extending the trace eliminate the spurious invariants? Did it reveal new invariants?**
**Yes, absolutely.** By providing a highly variable trace (complete games with high-value tiles such as 2048 and thousands of random method calls), Daikon automatically discarded the false generalizations about the bounded sets $\{2, 4\}$. ## Phase 4: Comparison

### 4.1 Daikon vs. `repOK()`

Below, the invariants inferred by Daikon from the **manual test** trace are compared with the representation properties formalized in the `repOK()` methods of `Cell` and `Board`:

| Invariant in `repOK()` | Inferred by Daikon (Manual Tests)? | Comment / Observation |
| --- | --- | --- |
| `Cell`: non-negative value (`value >= 0`) | **Yes** | `this.value >= 0` in `Cell:::OBJECT`. |
| `Cell`: value $\neq 1$ | **No** | Daikon did not infer the static exclusion of the value 1, since it is not a standard template in its library. |
| `Cell`: value is 0 or a power of 2 | **Partial** | Inferred only as a postcondition in `canMergeWith` and for active cells in `isEmpty()`, not as a global object rule. |
| `Board`: `size > 0` | **No** | It related `size` to the matrix dimension (`size == size(grid[])`), but did not deduce the explicit lower bound `size > 0`. |
| `Board`: `score >= 0` | **Yes** | Matches `this.score >= 0` in `Board:::OBJECT` exactly. |
| `Board`: non-null `grid` and square matrix | **Partial** | Deduces `grid != null` and the size of the rows, but does not validate the length of each individual column. |
| `Board`: no null cell and `cell.repOK()` | **No** | Exceeds the capabilities of Daikon's template library for nested quantification over multidimensional arrays. |

**New and useful invariants discovered by Daikon (Manual Tests):**

Daikon detected the property `this.spawner != null` in `Board:::OBJECT`, which represents a valid contract to avoid a null state in the tile-spawning strategy and was not originally covered by `Board.repOK()`.

#### Impact of the Extended Trace (Randoop + Fuzzer) on `repOK()`

By integrating the massive automated traces (**Randoop + Fuzzer**), Daikon not only reaffirmed the basic structure of `repOK()`, but also contributed behavioral contracts and algebraic domain laws that enrich the system's specification:

| Discovered Property / Contract | Inferred Invariant (Randoop + Fuzzer) | Contribution and relation to `repOK()` |
| --- | --- | --- |
| **`Cell`**: Conservation law in merging | `2 * this.value - return.value == 0` | Complements the static validation of `repOK()` by establishing the transition law of `Cell.mergeWith()` ($\text{return} = 2 \times \text{value}$). |
| **`Board`**: Score preservation on no-op moves | `(return == false) ==> (this.score == orig(this.score))` | Formalizes that on invalid or blocked moves in `Board.applyMove()`, the score stays identical to its state before the call. |
| **`Board`**: Range precondition on accesses | `row >= 0`, `col >= 0`, `row <= size(grid[]) - 1`, `col <= size(grid[]) - 1` | Defines the exact input bounds of `Board.getCell()` to guarantee that queries neither violate the object's integrity nor trigger uncontrolled exceptions (`IndexOutOfBoundsException`). |

### 4.2 Comparison of Oracle Approaches

| Source | Production method | Strengths | Weaknesses |
| :--- | :--- | :--- | :--- |
| **Manual assertions** | Written by hand | High semantic intent and precision. | Costly and prone to missing edge cases. |
| **`repOK()`** | Written by hand | Reusable at any point of the lifecycle. | Limited to what the programmer anticipates. |
| **Randoop** | Automatic capture of executions | Wide exploration with no manual effort. | Brittle assertions with no real semantics. |
| **EvoSuite** | Genetic algorithms/coverage | Maximizes code coverage. | Captures the current behavior (including bugs). |
| **Fuzzer (CLI)** | Random move sequences | Long games with high cells and scores. | Always plays on 4x4; does not explore other sizes or exceptions. |
| **Daikon** | Statistical dynamic inference | Discovers implicit relations between variables. | Sensitive to trace quality (*overfitting*). |

#### Evaluation on the Baseline Trace (Manual Tests)

Considering only the manual test suite, the combination of **semantic manual assertions and the `repOK()` method** proved to be the most useful approach. At this stage, Daikon produced too-strong or spurious invariants (such as restricting merges to $\{2, 4\}$ or assuming that `score` was always a multiple of the size), showing that dynamic inference over small suites requires mandatory human supervision.

#### Re-evaluation of Daikon after Extending with Randoop and the Fuzzer

Including the extended trace (**Randoop + Fuzzer**) significantly changes Daikon's usefulness in the development workflow:

* **Elimination of overfitting:** By exposing the tool to thousands of random executions and complete 2048 games, Daikon automatically discarded all the spurious numeric restrictions without human intervention.
* **Discovery of algebraic laws:** It revealed exact equations ($2 \times \text{this.value} = \text{return.value}$) that would have been laborious to formalize by hand.
* **Synergy between techniques:** Daikon shows its full potential not as a replacement for manual oracles, but as a **specification auditing and discovery tool**. Using Randoop and the Fuzzer to generate trace volume and Daikon to synthesize those executions into readable invariants gives the developer solid candidates to enrich the `repOK()` method and the regression assertions.

#### Contribution of EvoSuite

EvoSuite provides variety of **objects** (board sizes, `AddRandomTile`, exceptions) but not of **values**: on its own it eliminated only the `spawner` spurious invariant and recovered `size > 0`. Combined with the fuzzer, it also eliminated `{2, 4}`, `{4, 8}`, and `WINNING_VALUE > score`, and revealed that the score is always a multiple of 4 (see 3.4.2). More tests do not imply more varied data: each technique covers a different kind of variety.

**Conclusion:** The combination of **manual tests with semantic assertions and the `repOK()` method** is the most solid and reliable approach. Daikon works as an excellent assistant for discovering undocumented properties, but its output must be reviewed by a developer to discard false generalizations; moreover, if the test suite is not large and complete, it does not produce representative conditions for the methods or the objects. Adding the EvoSuite tests helped only partially: it eliminated one spurious generalization and recovered `size > 0`, but not the spurious invariants about cell values and the score, because more tests do not imply more varied data. Those were eliminated by the fuzzer games (see 3.4.2).
